# AGENTS.md

## Project overview

Bias Time Timer is a WXT Manifest V3 browser extension built with React, TypeScript, and Tailwind CSS. It converts a favorite person's birthday into two daily times, shows a live countdown, and delivers early and on-time system notifications.

The extension is designed to work without a developer-operated server. Do not add analytics, tracking, remote storage, or external data transmission unless the user explicitly requests and approves the accompanying privacy changes.

## Important commands

Use the Windows-compatible npm command in this repository:

```powershell
npm.cmd run typecheck
npm.cmd test
npm.cmd run build
npm.cmd run zip
```

Run type checking and the full test suite after code changes. Run a production build after changes to extension entrypoints, manifests, localization files, or browser APIs.

Do not edit `.output/` directly. It is generated by WXT.

## Project structure

- `entrypoints/background.ts`: background service worker and browser event listeners
- `entrypoints/popup/`: popup application entrypoint and styles
- `components/`: React UI components, including the main countdown, forms, and settings screen
- `lib/time.ts`: favorite-time calculation and notification delivery-window policy
- `lib/scheduler.ts`: alarm scheduling, system notifications, and notification-click handling
- `lib/storage.ts`: local and sync storage access
- `lib/migrations.ts`: persisted-data schema migrations
- `lib/images.ts`: device-local IndexedDB profile image storage
- `lib/backup*.ts`: JSON backup validation, export, and restore
- `lib/i18n.ts`: runtime locale selection and message lookup
- `public/_locales/`: Chrome-compatible Korean and English message catalogs
- `tests/`: Vitest unit tests

## Product invariants

### Notification timing

Favorite-time notifications are time-sensitive. `MAX_NOTIFICATION_DELAY_MS` is intentionally 60 seconds. An alarm processed after that window is skipped because a late notification has little product value. Do not increase this window or add delayed catch-up notifications without an explicit product decision.

Use `browser.alarms` for scheduled work. Do not replace alarm scheduling with `setTimeout` or `setInterval` in the background service worker.

### Data and privacy

- Favorite data and notification settings use extension storage.
- Profile photos remain device-local in IndexedDB and are excluded from sync storage.
- Backup files may contain favorite data and profile photos.
- Preserve schema migration compatibility when changing persisted types.
- Validate imported backup data before replacing existing data.
- Do not request additional extension permissions unless required by a user-approved feature.

### Browser compatibility

Prefer `browser` from `wxt/browser` over direct `chrome.*` calls. The current target is Chromium Manifest V3, including Chrome and Microsoft Edge. Keep browser-facing copy neutral unless a feature is genuinely Chrome-specific.

### Localization

All user-visible strings must use `t(...)`. Add matching keys to both:

- `public/_locales/ko/messages.json`
- `public/_locales/en/messages.json`

Keep both JSON files valid and include the locale assets in a production build check.

### Popup UI

The popup is 380 px wide with a minimum height of 560 px. Keep the main screen focused on the countdown and favorite management. Language, diagnostics, backup, restore, and other secondary controls belong in the settings screen.

Use accessible names or titles for icon-only buttons. Respect `prefers-reduced-motion` for decorative animation.

## Completion and source control

After completing a feature, fix, or other implementation task, always include the following in the final handoff:

1. A suggested Git commit subject and, when useful, a short commit body summarizing the changes.
2. A suggested next version number and the reason for the bump.

Use one appropriate SemVer step for the version suggestion:

- Patch for bug fixes, internal refactors, and small improvements
- Minor for new user-visible functionality
- Major for intentional breaking changes

The developer performs all commits. Do not run `git commit`, `git push`, create tags, or otherwise publish source-control changes. Do not change project version files merely because an implementation finished; propose the version first and update it only when the developer explicitly asks.

## Release checklist

For every store release:

1. Increase the version consistently in `package.json`, the root package entries in `package-lock.json`, and `wxt.config.ts`.
2. Run type checking, tests, and a production build.
3. Test the unpacked `.output/chrome-mv3` build in Chrome and Edge.
4. Run `npm.cmd run zip` and confirm `manifest.json` is at the ZIP root.
5. Update store listing or privacy documentation only when behavior, permissions, or data handling changed.

Do not commit a version bump unless all version locations agree.
